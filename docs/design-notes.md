# Design notes: the gaps that are still open

Most of what the Python SDK does and this one didn't has since been built —
resources, images, caching, retries, secrets, container reuse, checkpoints and
the control plane all landed as their own change. What follows is the
remainder: four gaps that are not a missing afternoon's work, and what it would
actually take to close each one.

They are written down rather than half-built because a half-built version of
any of them would break the property the SDK is organised around — that the
same file runs in-process and on a cluster, and behaves the same either way.

---

## 1. Rich task I/O

**Today:** `String`, `Int`, `Float64`, `Bool`. Zero to three positional
arguments. One return value.

**Why it stops there.** Values cross an action boundary as strings, so
`from_wire[T]` has to rebuild a `T` from one. That is a compile-time dispatch
over a *closed* set of types (`flyte/_wire.mojo`):

```mojo
comptime if T == String:
    return rebind[T](String(s)).copy()
elif T == Int:
    ...
```

Python does this with a protocol — anything implementing it round-trips. Mojo
1.0 has no equivalent trait to constrain on, and no way to retroactively
conform a stdlib type, so the set cannot be opened up from inside the SDK.

**What is cheap.**

*Files and directories.* `flyte.io.File` and `Dir` are references to blob
storage, and a reference is a string. A Mojo `File` struct wrapping a URI
round-trips through the existing wire untouched; the shim resolves it to a
local path before the binary runs and uploads whatever the binary wrote after.
This is the single highest-value item on this page and it needs no language
changes.

*More arities and multiple results.* The wrappers in `flyte/_core.mojo` are
already generated by a script — arity 4, 5, 6 is a loop bound. Multiple return
values need a small tuple type whose encoder concatenates fields, which is the
same trick `_spec.mojo` already uses.

**What is blocked.** User-defined structs. Two ways out, neither good today:

- A Mojo trait for construct-from-string, so `from_wire` can constrain on it
  instead of enumerating. This is language work, not SDK work.
- Generating the codec from the struct declaration in source. The SDK already
  reads task bindings out of source and it is the most fragile thing in it —
  adding a parameter to a binding once silently broke action naming for every
  action in a program. Extending that to type declarations would multiply a
  known weakness.

**Recommendation.** Do files and directories now; do arities and tuples when
someone needs them; wait for the language on structs.

## 2. Concurrency beyond a fan-out

**Today:** `map[...]` runs one task over one list, in parallel. Anything else
runs one after another.

**What is missing** is `asyncio.gather` over *different* tasks — launch an
extract and a lookup together, wait for both.

**Why it is blocked.** A gather has to hold the calls before it runs them, and
a call is a function plus its arguments. Mojo 1.0 will not let that be stored:

```mojo
var jobs = List[def() raises -> String]()
# error: 'List' parameter 'T' has 'Movable' type, but value has type
#        'AnyTrait[def() raises -> String]'
```

The `escaping` effect that would have made a closure storable is gone in 1.0
("the 'escaping' function effect is no longer supported"), and the capture-list
syntax is rejected in that position.

A batch that stores only *names and arguments* — `("etl.score", ["7"])` — does
work on a cluster, because the shim can look the name up. It has no local path
at all: nothing in a local run maps a name back to a function. Shipping it
would mean a construct that works remotely and cannot run on your laptop, which
is exactly the split this SDK exists to avoid.

**What is cheap.** Fanning out over pairs — one task, a list of two-argument
tuples — is a real improvement and needs none of the above. So is running two
independent fan-outs concurrently, since each is already one request.

**Recommendation.** Wait for Mojo function values to be storable; take the
pairs fan-out in the meantime.

## 3. Apps and serving

**Today:** none. `flyte.serve`, FastAPI, vLLM have no counterpart.

**Why it is a different shape.** Every action here is *exec the binary, read
its result, exit*. An app is the opposite: a process that stays up and answers
requests. Nothing about the current architecture carries over except the build.

Two ways to build it:

1. **The shim serves; the binary answers.** The generated shim runs FastAPI and
   keeps one long-lived binary behind it, handing each request over the pipe
   protocol that already exists. Small change, and it reuses everything —
   but every request pays a Python hop, which is most of what you were trying
   to avoid by writing the task in Mojo.
2. **The binary serves.** Mojo owns the socket; the shim only supervises it and
   reports health. This is the version worth having, and it needs an HTTP
   server in Mojo.

**Why it may be the most interesting item here.** Serving is where compiled
code earns its keep — a request handler is exactly the workload where the
interpreter overhead this SDK removes is measured per request rather than per
pod. The rest of this page makes the SDK more complete; this would make it
faster than the thing it is a port of.

**Recommendation.** Design 2, once there is a reason to spend the time on it.

## 4. Deployment and scheduling

**Today:** run-only. Nothing is registered, so nothing else can call a Mojo
task and nothing can be scheduled.

**Why they are one item.** A `Cron` or `Trigger` attaches to a *deployed* task.
You cannot schedule what has no stable identity, so scheduling is a small
change that sits on top of a moderate one.

**What deployment needs.** The generated shim currently lands in a
content-hashed build directory and exists for the length of one run, so there
is no task identity to register. Three pieces:

- **Stable naming.** Today the environment is named after the program file
  (`mojo_pipeline`). A deployed task needs a name its callers can rely on,
  which means taking it from the `TaskEnvironment` rather than the filename.
- **A version.** The binary is already content-hashed — that hash is the
  version, and it has exactly the right property: it changes when the Mojo
  changes and not otherwise.
- **A `deploy()` entry point** that builds, bundles and registers without
  launching, so `flyte deploy` has something to talk to.

Scheduling is then `Trigger` and `Cron` in the spec that every action already
carries, applied at registration instead of at launch.

**What it unlocks.** A Python workflow calling a Mojo task by name. That is a
better argument for this SDK than anything on this page: today Mojo is the
thing that drives Flyte, and deployment makes it a thing Flyte can call.

**Recommendation.** Highest value of the four after files and directories.

---

## If you are picking one

1. **Files and directories** (§1) — cheap, unblocks real workloads, no language
   changes.
2. **Deployment** (§4) — makes Mojo tasks callable by everyone else, and
   scheduling comes nearly free afterwards.
3. **Serving** (§3) — the only item that makes this faster rather than more
   complete.
4. **Concurrency** (§2) — wait for the language.
